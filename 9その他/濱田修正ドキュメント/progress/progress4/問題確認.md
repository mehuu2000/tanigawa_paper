# 問題確認

## 調査対象

- `4プログラム/jalc-to-solr.ipynb`
- `4プログラム/create_references.ipynb`
- `4プログラム/create_references_none_typo.ipynb`
- `4プログラム/create_references_none_typo_crossref.ipynb`

## 確認した問題

Solr に登録している著者表記と、正例データとして作成している参考文献文字列側の著者表記が、特に英語著者で一致していない可能性が高い。

そのため、英語著者を含む文献では、検索後の RC / CC / MC の類似度計算時に著者部分のトークン一致が低下する可能性がある。

## Solr 登録側の英語著者表記

`jalc-to-solr.ipynb` では、著者情報は主に `creator` と `first_author` に登録される。

### `creator`

英語著者の場合、以下のような表記が登録される。

| 登録されるもの | 例 |
|---|---|
| `last_name` | `Nontachai` |
| `first_name` | `TITHIPONGTRAKUL` |
| `first_name` を分割した各要素 | `TITHIPONGTRAKUL` |
| `first_name` 由来のイニシャル | `T` |
| 複数語 first_name の場合のイニシャル順列 | `A`, `H`, `AH`, `HA` など |

一方で、以下のような完成形の英語著者表記は登録されていない。

| 登録されないもの | 例 |
|---|---|
| 空白ありのフルネーム | `Nontachai TITHIPONGTRAKUL` |
| 空白なしのフルネーム | `NontachaiTITHIPONGTRAKUL` |
| カンマ + イニシャル表記 | `Nontachai, T.` |

### `first_author`

英語筆頭著者の場合、基本的には `last_name` のみが登録される。

| 登録されるもの | 例 |
|---|---|
| `last_name` | `Nontachai` |

`first_author` にも、以下のような表記は登録されていない。

| 登録されないもの | 例 |
|---|---|
| 空白ありのフルネーム | `Nontachai TITHIPONGTRAKUL` |
| 空白なしのフルネーム | `NontachaiTITHIPONGTRAKUL` |
| カンマ + イニシャル表記 | `Nontachai, T.` |

## 正例データ作成側の英語著者表記

正例データ作成側では、MongoDB の `creator_list[*].names` から `[last_name, first_name]` を取り出し、それを各引用スタイルに変換している。

英語著者の表記は、スタイルごとに異なる。

| 引用スタイル | 実装上の作り方 | 例 |
|---|---|---|
| JSAI | `last_name + ", " + first_name[0] + "."` | `Nontachai, T.` |
| IPSJ | `last_name + ", " + first_name[0] + "."` | `Nontachai, T.` |
| LSJ | `last_name + first_name` | `NontachaiTITHIPONGTRAKUL` |

特に LSJ では、言語判定なしで以下のように連結している。

```python
for name in creator_list:
    tmp.append(name[0] + name[1])
```

そのため、日本語著者では `山田太郎` のように自然な表記になるが、英語著者では `NontachaiTITHIPONGTRAKUL` や `AdnanAKMAL` のように空白なしで連結される。

## 比較

`Nontachai` / `TITHIPONGTRAKUL` を例にすると、Solr 登録側と正例データ側は以下のようにずれている。

| 場所 | 表記 |
|---|---|
| Solr `creator` | `Nontachai`, `TITHIPONGTRAKUL`, `T` |
| Solr `first_author` | `Nontachai` |
| JSAI 正例 | `Nontachai, T.` |
| IPSJ 正例 | `Nontachai, T.` |
| LSJ 正例 | `NontachaiTITHIPONGTRAKUL` |

このため、正例データ側に出てくる `Nontachai, T.` や `NontachaiTITHIPONGTRAKUL` は、Solr 側にそのままの形では登録されていない。

## RC / CC / MC への影響

RC は、参考文献文字列側のトークンが候補文献メタデータ側にどれだけ含まれるかを見る指標である。

```text
RC = 共通トークン数 / 参考文献文字列側のユニークトークン数
```

そのため、正例データ側の英語著者表記と Solr 側の英語著者表記が一致しない場合、著者部分の共通トークンが減り、RC が下がる可能性がある。

CC は、候補文献メタデータ側の各フィールドが参考文献文字列側にどれだけ含まれるかを見る指標である。

そのため、`first_author` に `Nontachai` しか登録されていない一方で、参考文献文字列側が `NontachaiTITHIPONGTRAKUL` のような連結表記になっている場合、著者フィールドの一致が不安定になる可能性がある。

MC は RC と CC を合成した指標であるため、英語著者表記のずれは MC にも影響する。

## 現時点の結論

英語著者を含む文献でスコアが落ちる原因の一つとして、Solr 登録側と正例データ作成側の著者表記の不一致が考えられる。

特に LSJ 形式では、英語著者を `last_name + first_name` で空白なし連結しているため、Solr 側の登録表記と噛み合っていない。

次に修正する場合は、少なくとも以下のどちらか、または両方を検討する必要がある。

- 正例データ作成側の LSJ 英語著者表記を、`last_name + " " + first_name` のように空白ありへ修正する。
- Solr 登録側にも、英語著者の空白ありフルネームや引用スタイル用表記を追加する。

## 追加確認: title / subtitle の不一致

著者表記以外に、タイトルとサブタイトルの結合方法にも不一致がある。

Solr 登録側では、`subtitle` がある場合に `title + " | " + subtitle` を登録している。

```python
title_list.append(t.get("title"))
if (subtitle := t.get("subtitle")) is not None:
    title_list.append(t.get("title") + " | " + subtitle)
```

一方、正例データ作成側では、`subtitle` がある場合に `title + " " + subtitle` として参考文献文字列を作成している。

```python
title_text = title
if subtitle != "":
    title_text = title_text + " " + subtitle
```

比較すると以下のようになる。

| ケース | Solr 登録側 | 正例データ作成側 |
|---|---|---|
| `subtitle` なし | `title` | `title` |
| `subtitle` あり | `title` と `title \| subtitle` | `title subtitle` |

`subtitle` がない場合は、Solr 側も正例データ側も `title` のみになるため不一致は起きにくい。

しかし、`subtitle` がある場合は、Solr 側と正例データ側で表記が確実にずれる。

日本語タイトルでは `wakati.py` が文字 2-gram を生成するため、正例データ側の `title subtitle` では「タイトル末尾 + サブタイトル先頭」をまたぐ 2-gram が生成される。

一方、Solr 側の `title | subtitle` では `|` が区切り文字として扱われるため、この境界 2-gram が生成されない。

そのため、`subtitle` を持つ文献では RC が下がる可能性がある。

### 対応方針

正例データ作成側は変更せず、Solr 登録側を正例データ側に合わせる。

具体的には、Solr 登録時の `get_title()` で `title + " | " + subtitle` ではなく、`title + " " + subtitle` を登録する。

```python
title_list.append(t.get("title"))
if (subtitle := t.get("subtitle")) is not None:
    title_list.append(t.get("title") + " " + subtitle)
```

`title` 単体の登録は維持するため、`subtitle` なしの文献や、タイトル単体での検索には影響しにくい。

## 追加確認: 互換漢字による日本語著者判定漏れ

正例データ作成側で、互換漢字を含む日本語著者が英語著者として扱われる問題が確認された。

例:

```text
⼭⼝聖太
⽯⽥知也
```

これらの `⼭` や `⼝`、`⽯`、`⽥` は、人間には通常の漢字に見えるが、Unicode 上は通常の CJK 統合漢字ではなく互換漢字・康熙部首系の文字である。

そのため、既存の `has_japanese()` では日本語として判定されない。

既存の判定:

```python
def has_japanese(text):
    return bool(re.search(r'[\u3040-\u309F\u30A0-\u30FF\uFF66-\uFF9F\u4E00-\u9FFF]', text))
```

この判定は `\u4E00-\u9FFF` の通常漢字範囲を見ているため、互換漢字が含まれる場合に判定漏れが起きる。

確認例:

```text
⼭⼝ -> 日本語判定 False
NFKC(⼭⼝) = 山口 -> 日本語判定 True

⽯⽥ -> 日本語判定 False
NFKC(⽯⽥) = 石田 -> 日本語判定 True
```

この影響により、正例データ作成時に日本語著者が英語著者扱いされる可能性があった。

例:

```text
⼭⼝, 聖.
```

本来は日本語著者として以下のように扱うべきである。

```text
⼭⼝聖太
```

### 対応方針

正例データ作成側の `has_japanese()` で、判定前に NFKC 正規化を行う。

```python
def has_japanese(text):
    text = unicodedata.normalize("NFKC", text or "")
    return bool(re.search(r'[\u3040-\u309F\u30A0-\u30FF\uFF66-\uFF9F\u4E00-\u9FFF]', text))
```

これにより、互換漢字を含む日本語著者も日本語として判定される。

確認結果:

```text
['⼭⼝', '聖太'] => ⼭⼝聖太
['⽯⽥', '知也'] => ⽯⽥知也
['Nontachai', 'TITHIPONGTRAKUL'] => Nontachai TITHIPONGTRAKUL
```

評価時の `wakati.py` でも NFKC 正規化は行われるため、トークン化だけを見れば `⼭⼝ 聖太` のように空白が入っていても大きな問題にはなりにくい。

ただし、参考文献文字列としての表記整合性を保つため、生成時点で日本語著者は空白なしの姓名結合にする方が正しい。

## 追加確認: 負例データに Crossref 由来行が残っている問題

現在の環境は、MongoDB / Solr から Crossref データを除外し、JaLC データのみで再構築している。

一方で、負例データは Crossref データが入っていた過去環境で作成されたものを継続利用していた。

そのため、負例データ内に、現在の JaLC のみの環境には存在しない Crossref 由来文献を元にした行が残っている可能性があった。

この状態で評価すると、以下の問題が起きる。

- 評価対象の負例データが、現在の Solr 登録対象と一致しない。
- Crossref 由来の負例は、現在の検索対象に正解元データが存在しない前提になり、環境条件が正例データと揃わない。
- 閾値取得や再評価で、JaLC のみ環境に対する純粋な結果ではなくなる。

### DOI による直接判定ができない理由

負例ファイルには DOI が直接書かれていない。

負例は、元文献のメタデータを使いつつ、Gemini 生成タイトルに置き換えて作られている。

そのため、負例テキスト単体から DOI を直接読み取って Crossref 由来かどうかを判定することはできない。

### 判定方針

旧 DOI リストと Crossref なし DOI リストを比較し、Crossref 除外により削除された DOI を特定する。

その上で、負例データの各行から Gemini 生成タイトルを抽出し、`llm_create_titles.txt` または `llm_create_titles_2.txt` の行順に対応させる。

対応した行番号から旧 DOI リストの DOI を復元し、その DOI が Crossref なし DOI リストに存在しない場合、Crossref 由来の負例行と判定する。

### 確認結果

予備実験用:

- 旧 DOI: 712件
- Crossref なし DOI: 701件
- DOI 差分: 11件
- 負例データ上の削除対象: 10件

評価実験用:

- 旧 DOI: 863件
- Crossref なし DOI: 843件
- DOI 差分: 20件
- 負例データ上の削除対象: 19件

DOI 差分より負例データ上の削除対象が1件少ないのは、該当文献が負例生成時の `title != llm_create_title` 条件を満たさず、そもそも負例ファイルに出力されていなかったためと考えられる。

### 削除対象

削除対象は以下の通り。

- 予備実験用負例: 各スタイルの 1〜10行目
- 評価実験用負例: 各スタイルの 1〜19行目

JSAI / IPSJ / LSJ は同じループで同時生成されているため、削除する場合は3スタイルで同じ行番号を同時に削除する必要がある。

## 追加確認: 空白のみの著者が Solr 登録対象になっていた問題

Solr 登録処理の修正後、登録件数が想定より少なく見える問題が発生した。

確認した件数は以下の通り。

- 旧ロジックの登録対象数: 3,617,035件
- 英語著者のフルネーム追加後、一時的に確認された登録件数: 3,617,048件
- 空白著者除外を含む修正後の登録対象数: 3,617,024件

原因は、旧ロジックでは `first_name` や `last_name` が全角空白や半角空白だけの場合でも、`creator_list` が空ではないと判定され、Solr 登録対象になっていたためである。

英語著者の `last_name first_name` 表記を追加した際、この空白のみの著者にも処理が反応し、一時的に13件多く登録対象になった。

その後、著者名を `.strip()` して空白のみの値を除外するようにしたため、この13件は登録対象外になった。

さらに、旧ロジック時点でも空白のみの著者として登録対象に含まれていた11件も除外されるようになった。

したがって、最終的な件数は以下のように整理できる。

```text
3,617,048 - 13 - 11 = 3,617,024
```

### 旧ロジックでのみ登録対象になっていた DOI

以下の11件は、著者情報が空白のみであったため、修正後ロジックでは登録対象外になる。

```text
10.11441/shinshumedj.54.229
10.11475/sabo.61.1_0
10.11164/jjsps.49.4_001
10.11164/jjsps.49.4_959
10.11164/jjsps.49.4_961
10.11164/jjsps.49.4_9999
10.11164/jjsps.49.6_1160
10.11164/jjsps.49.6_1166
10.11164/jjsps.49.6_1182
10.11164/jjsps.49.6_9999
10.15114/smj.71.83
```

代表例として、以下のように `first_name` が全角空白のみになっていた。

```text

```

このような文献を登録対象に含めると、著者情報を持たない文献が検索対象に混入する。

そのため、今回の修正後の 3,617,024件を正しい Solr 登録件数として扱う。

## 追加確認: 再評価で落ちた正例・負例の原因

該当データについて、実際に Solr / MongoDB の登録値と参考文献文字列を比較し、原因を確認した。

```text
LSJ:  0.9767441860465116
欠落トークン: 1
```

### 原因

原因は、タイトル先頭の数字 `1` の扱いである。

Solr 側では、候補文献の title フィールド単体をトークン化する。

このとき `wakati.py` の以下の処理により、セグメントリストの先頭が数字のみの場合、引用番号とみなして削除される。

```python
if (len(segment_list) >= 5) and re.match(r"^\d+$", segment_list[0]):
    segment_list.pop(0)
```

候補文献側の title は以下のようにタイトル先頭から始まる。

```text
1 日 5 分で...
1年に膝の手術を...
```

そのため、候補文献側では `1` トークンが削除される。

一方で、参考文献文字列側は著者名から始まる。

```text
緒倉珠巳：1 日 5 分で...
鈴木岬，郷田悠，来間弘展：1年に...
```

この場合、`1` は参考文献文字列全体の先頭ではないため、引用番号とは判定されず、トークンとして残る。

その結果、参考文献文字列側には `1` トークンが存在するが、候補文献側には存在しない。

RC では参考文献文字列側のトークンが候補文献側にどれだけ含まれるかを見るため、この1トークンの欠落によりスコアが下がった。

今回の RC 閾値は `0.9846` と高いため、1トークンの欠落でも case2 になった。

これは正例データ作成時の title / subtitle 結合ミスではなく、スコア計算時に「参考文献文字列全体」と「Solr の各フィールド」を別々にトークン化していることによる差である。

## 負例の誤検出

負例では、RC で1件、CC で2件が誤検出された。

主な原因は、負例生成時のタイトル変換が実文献タイトルにかなり近く、かつ年や第一著者が別文献と一致してしまったことである。

### RC 誤検出: `10.24805/jiaio.2.3_109`

参考文献文字列:

```text
LSJ:
角田梨紗子・金森肇・徳田浩一・北谷栞（2021）「東北大学病院耳鼻咽喉・頭頸部外科における新型コロナウイルススクリーニングPCR検査の現状調査」『日本耳鼻咽喉科免疫アレルギー感染症学会』
```

誤同定候補:

```text
doi: 10.24805/jiaio.2.3_109
title: 東北大学病院　耳鼻咽喉・頭頸部外科における新型コロナウイルススクリーニングPCR検査の現状調査
issued: 2022
journal: 日本耳鼻咽喉科免疫アレルギー感染症学会誌
```

RC スコア:

```text
RC = 0.9850746268656716
欠落トークン: 2021
```

負例では年を `2021` にしているが、候補文献は `2022` である。

しかし、年以外の著者・タイトル・学会名がほぼ一致していた。

特に、元タイトルと負例タイトルの差は空白の有無が中心である。

```text
元タイトル:
東北大学病院　耳鼻咽喉・頭頸部外科における新型コロナウイルススクリーニングPCR検査の現状調査

負例タイトル:
東北大学病院耳鼻咽喉・頭頸部外科における新型コロナウイルススクリーニングPCR検査の現状調査
```

`wakati.py` では日本語間の空白は正規化されるため、この差はほぼスコアに影響しない。

そのため、年だけが異なっていても RC 閾値を超え、誤検出になった。

### CC 誤検出: `10.51116/kokyurigakuryohogaku.7th.Meeting.0_SJ-2`

参考文献文字列:

```text
大島洋平，佐藤晋，吉岡佑二ほか：肺移植術後の遠隔期における健康関連QoLの実態と関連因子の検討，日本呼吸理学療法学会 （2021）．
```

### CC 誤検出: `10.51052/jarcds.3.0_62`

参考文献文字列:

```text
IPSJ:
町田隆司，今里恵子：質疑応答について，日本離婚・再婚家族と子ども研究学会 （2021）．

JSAI:
町田，今里：質疑応答について，日本離婚・再婚家族と子ども研究学会 (2021).

LSJ:
町田隆司・今里恵子（2021）「質疑応答について」『日本離婚・再婚家族と子ども研究学会』
```

この負例の生成元は以下である。

```text
生成元 DOI: 10.51052/jarcds.4.0_106
title: 質疑応答
issued: 2022
volume_issue: 4 / 0
page_range: 106-113
authors: 町田隆司 / 今里恵子 / 小田切紀子
```

負例生成時に年を `2022` から `2021` に変更し、LLM 生成タイトル `質疑応答について` を使っている。

しかし、Solr には以下の別文献が存在していた。

```text
誤同定候補 DOI: 10.51052/jarcds.3.0_62
title: 質疑応答
issued: 2021
volume_issue: 3 / 0
page_range: 62-68
authors: 町田隆司
```

つまり、DOI は異なる。

```text
生成元 DOI:   10.51052/jarcds.4.0_106
誤同定候補:   10.51052/jarcds.3.0_62
```

ただし、CC の評価対象は `first_author`, `title`, `journal`, `issued` であり、著者全体・巻号・ページは見ない。

そのため、以下のように候補文献側の4フィールドがすべて負例文字列に含まれる。

```text
first_author:
候補 = 町田隆司
負例 = 町田隆司，今里恵子
=> 含まれる

title:
候補 = 質疑応答
負例 = 質疑応答について
=> 含まれる

journal:
候補 = 離婚・再婚家族と子ども研究
負例 = 日本離婚・再婚家族と子ども研究学会
=> 含まれる

issued:
候補 = 2021
負例 = 2021
=> 一致
```

その結果、CC は `1.0` になった。

このケースでは、負例生成時に年を1年前にずらしたことが、偶然 Solr 内に存在する前年の類似文献と一致する原因になっている。

また、CC が `creator` 全体ではなく `first_author` のみを見るため、生成元には `今里恵子` や `小田切紀子` が含まれていても、候補側にそれらが存在しないことは減点されない。

### まとめ

正例の検出漏れは、タイトル先頭の数字がトークン化時に候補側だけ削除されることが原因である。

負例の誤検出は、以下が原因である。

- LLM 生成タイトルが実タイトルとほぼ同じ、または実タイトルを包含している。
- 負例の学会名が、候補文献の journal 名を包含している。
- CC は候補文献側の情報が参考文献文字列に含まれるかを見るため、負例側に余分な語があっても減点されにくい。
- CC は `first_author` のみを見ており、著者数の違いや2人目以降の違いを減点できない。
- 年を1年前にずらした負例が、実際に存在する前年の類似文献と一致する場合がある。
